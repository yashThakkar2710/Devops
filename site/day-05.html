EC2, EBS and AMIs

Everything so far has been empty plumbing. Today it carries something — and the debugging session at the end turned out to be worth more than the building.

Three switches, all required

Day 3 showed a route is not enough. Day 4 showed a public IP is not enough. Both are true at once. Flip them.

In a subnet you built yourself, auto-assign public IP is OFF by default.

AWS enables it in the default VPC, which is why tutorials never mention it. A hand-built subnet assumes you meant to be deliberate — so nothing becomes public without being asked for.

One machine, two addresses

10.0.1.238      private — what it calls itself
13.233.89.217   public  — what the internet reaches

The instance has no idea it has a public address. The internet gateway translates on the way in. Ask the server its IP and it says 10.0.1.238.

User data, and what an AMI really captures

#!/bin/bash
dnf install -y nginx
systemctl enable --now nginx
echo "<h1>Hello from $(hostname -f)</h1>" > /usr/share/nginx/html/index.html

A script that runs once, as root, the first time an instance boots — before anyone logs in. It is the beginning of infrastructure as code, and it is how Auto Scaling works at all: when a server is created at 3am, nobody is there to SSH in.

Then an AMI was made, and web-2 launched from it with no user data

[ec2-user@ip-10-0-1-230 ~]$ curl localhost
<h1>Hello from ip-10-0-1-238.ap-south-1.compute.internal</h1>

The machine is .230. The page says .238. That is web-1's name.

The script ran once, on web-1, and $(hostname -f) was replaced by its answer at that moment. The file now literally contains that text. The AMI copied the file, not the script that wrote it.

Photographing a whiteboard.

Someone wrote "Today is Monday" and you took a photo. On Tuesday the photo still says Monday — you captured the writing, not the person who wrote it.

This is a real production problem. AWS regenerates what matters most — SSH host keys, the actual hostname — but anything your script wrote into a file is frozen.

Which makes them different tools

user data

a script run at boot

  • Flexible — change anytime
  • Slow — installs every boot
  • Can differ per instance
  • Things that DO change

AMI

a disk prepared in advance

  • Fixed — rebuild to change
  • Fast — nothing to install
  • Every copy identical
  • Things that DON'T change
Auto Scaling, a server created during a traffic spike:
  AMI with software baked in   ~30 seconds
  blank AMI + user data        ~3 minutes

three minutes is a long time when the site is overloaded

Storage: disks that outlive machines

instance  ◄══ network ══►  EBS volume

EBS is a disk on the network, not a drive bolted into a server. Which is why the disk and the computer have separate lifetimes: terminate the instance and the volume can survive; detach it and attach it elsewhere; snapshot it while it is running.

an EBS volume lives in ONE availability zone
one volume attaches to one instance at a time

Volume types

→gp3 — the default answer. boot disks, most workloads
→io2 — databases needing guaranteed consistent IOPS
→st1 — big sequential throughput: logs, data processing
→sc1 — cheapest, rarely accessed

gp3 replaced gp2. With gp2, speed was tied to volume size, so people bought oversized disks purely to get IOPS. gp3 sets size and speed separately. A question about "paying for unused capacity to get performance" is pointing at gp3.

The other kind of disk

EBS             over the network    SURVIVES stop/start
instance store  physically inside   WIPED on stop, permanently

Extremely fast, completely temporary — it is a different physical machine when it starts again.

Snapshots are the bridge between zones

EBS volume   ONE availability zone
snapshot     REGIONAL

A volume cannot be attached across AZs. Snapshot it and restore into the other zone — and the same mechanism copies across regions for disaster recovery.

Snapshots are incremental: the first captures everything, later ones only changed blocks. Deleting an old one is safe. Observed here: an 8 GiB volume produced a 1.7 GiB snapshot — only used blocks are stored.

AMI and snapshot are different objects

AMI       instructions: boot from snap-xxx, 8 GiB, this is root
snapshot  the actual bytes

The "delete associated snapshots" box is unchecked by default.

Deregistering an AMI does not delete its snapshot. Click straight through and the data keeps billing forever. Worth generalising: on an AWS delete dialog, the default is usually the expensive one.

root volume      DeleteOnTermination = true    goes with the instance
extra volumes    DeleteOnTermination = false   survive, billing quietly

Drop versus reject

Deleting the HTTP rule produced a hang, not an error. That distinction is the most useful diagnostic in networking.

DROP     the packet is binned, nothing sent back
         → the sender waits for a reply that never comes → TIMEOUT

REJECT   a refusal is sent back
         → the sender knows at once → INSTANT error

Security groups and NACL denies always drop, never reject.

→hangs, then times out — nothing replied. firewall, wrong IP, or no route.
→"Connection refused", instantly — something replied. the network is fine, the app is down.
→"Could not resolve host" — DNS. never got as far as connecting.

These send you in opposite directions.

People spend hours checking firewalls when the error already told them the application had crashed. Dropping rather than rejecting is deliberate — a rejection confirms a machine exists, and silence gives an attacker nothing.

The debugging session

web-2 timed out in the browser while web-1 had worked. Seven steps, no guessing.

1 The failure was a timeout, not "connection refused" so the packet never reached nginx — not an application problem narrowed
2 Checked the security group — port 80 from 0.0.0.0/0 present the first hypothesis was wrong ruled out
3 SSH to web-2 worked route table, internet gateway, public IP and instance all proven fine — only port 80 affected big cut
4 From inside web-2: systemctl status nginx, ss -tlnp, curl localhost active, listening on 0.0.0.0:80, returns 200 — the server is perfect server OK
5 From inside web-2, curl both public IPs both 200 OK — the whole AWS side is proven working AWS OK
6 curl from the Windows machine, both IPs both 200 OK — the network path from home is proven working path OK
7 Therefore: the browser Chrome's "Always use secure connections" was rewriting http:// to https://. Port 443 was closed, so it hung. FOUND

Four tests, each eliminating a whole category.

No guessing at any point. That is the difference between fixing problems and restarting things until they work.

And the lesson underneath: your test tool can be the bug. Browsers perform HTTPS upgrades, caching, prefetching and extension interference. curl does exactly what you typed and nothing more. Diagnose with curl first — if curl works and the browser does not, stop looking at the server.

How you pay for EC2

→On-Demand — per second, no commitment. most expensive.
→Reserved Instance — commit 1 or 3 years. ~40-60% off.
→Savings Plans — commit to $/hour. ~40-70% off, and flexible across instance types, Lambda and Fargate.
→Spot — spare capacity, reclaimed on 2 minutes' notice. up to 90% off.
→Dedicated Host — a whole physical server. for per-socket licensing.
✅ Spot  batch jobs, rendering, CI, big data — anything interruptible
❌ Spot  your database. your only web server.

Exam phrasing: "fault-tolerant", "can be interrupted", "flexible start and end times" → Spot. "Steady state, always on" → Reserved or Savings Plans. "Bring your own licence" or "per-socket licensing" → Dedicated Host.

Test yourself

  1. Name the three independent things required before the internet can reach a server. What happens if only two are present?
  2. Why is auto-assign public IP off by default in a subnet you built, but on in the default VPC?
  3. Your server says its IP is 10.0.1.238, but you reach it at 13.233.89.217. Explain.
  4. You launch from an AMI with no user data. nginx is running. Why?
  5. The page shows a different hostname from the machine serving it. Explain exactly why.
  6. When would you use user data rather than bake something into an AMI? Give the Auto Scaling reason.
  7. Why can an EBS volume not be attached to an instance in another AZ — and how do you move it anyway?
  8. You stop an instance. What happens to EBS data? To instance store data?
  9. Why did gp3 replace gp2? What problem did gp2 create?
  10. A connection hangs then times out. A different one says "connection refused" instantly. What does each tell you, and why do they need opposite fixes?
  11. Why do firewalls drop packets rather than rejecting them?
  12. You deregister an AMI. What is left behind, and why does the console not clean it up by default?
  13. You terminate an instance with two volumes attached. What happens to each?
  14. Nightly video processing that can restart if interrupted — which purchasing option? Why not for a database?
  15. Your browser times out but curl works from the same machine. What have you proven, and where do you look next?
