IAM in depth

Every action in AWS passes through one question: is this allowed? Nothing else answers it. Firewalls and networks come later and protect different things — who may do what is entirely policies.

A policy is a JSON file, and nothing more

Here is the most powerful permission in AWS, in full.

{
    "Version": "2012-10-17",
    "Statement": [
        { "Effect": "Allow", "Action": "*", "Resource": "*" }
    ]
}

That is AdministratorAccess. Five meaningful lines, no special status. It is powerful only because * means everything.

The four parts — click each one

Pick a part Click any coloured key above.

Read it as a sentence: allow the action s3:GetObject on my-bucket/*, if the conditions hold. Actions are service:Operation. Resources are ARNs — which is why day 1 spent time on them. Policies are built out of ARNs.

The bucket and the papers inside it

The most common S3 permission bug, and it looks correct in the console.

arn:aws:s3:::company-reports        the bucket itself
arn:aws:s3:::company-reports/*      every object inside it
                            ↑
                        this slash matters

A filing cabinet and the papers in it. Listing the cabinet is an action on the cabinet. Reading a paper is an action on the paper.

s3:GetObject   on company-reports/*   ✓ correct
s3:ListBucket  on company-reports/*   ✗ silently grants nothing

The second one is listed, looks fine, and does nothing — because ListBucket acts on the bucket ARN, which has no /*. The result: someone who can download a file whose name they know, but cannot see what exists.

A rule of thumb that works

action name contains Object  →  the paper   →  needs /*
action name contains Bucket  →  the cabinet →  no /*

ListBucket has "Bucket" in the name. That is the clue.

But withholding ListBucket is often the point

→GetObject only — a thief fetches files whose names they can guess
→GetObject + ListBucket — a thief enumerates everything, then downloads all of it

An app fetching avatars/user-12345.jpg builds that key itself and never browses. Giving it ListBucket turns a small breach into a total one.

Listing is the permission that turns "I can read a file" into "I can read everything."

Ask of every policy: does this thing need to look around, or does it already know what it wants? That is most of what least privilege means in practice.

Three states, and which one wins

Toggle the policies and watch the verdict.

explicit Deny   ███████  beats everything
explicit Allow  ████
implicit deny   █        the default

Everything starts denied. Policies only ever add — a brand-new IAM user with no policies can sign in and do literally nothing.

Why this matters: Deny is the only subtraction

Allow + Allow = more allowed      there is no way to subtract

You cannot enforce anything with Allow. Deny winning is what lets one policy override every Allow in the account at once, without editing any of them.

Allow  →  "here is what you CAN do"       permissions
Deny   →  "here is what NOBODY may do"    guardrails

Teams hand out Allow freely. Security writes a handful of Deny policies nobody can escape. Two different jobs — and only the second one needs Deny.

Making MFA compulsory

The guardrail pattern, built and tested on this account.

{
    "Effect": "Deny",
    "NotAction": [ "iam:CreateVirtualMFADevice", "iam:EnableMFADevice",
                   "iam:GetUser", "iam:ListMFADevices", ... ],
    "Resource": "*",
    "Condition": {
        "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
    }
}

NotAction — the inverse

Action     →  deny THESE things
NotAction  →  deny EVERYTHING EXCEPT these things

So: deny everything except the MFA-setup calls, whenever MFA is absent. That carve-out is the lockout trap avoided — without it, a user with no MFA could never add MFA and would be stuck permanently.

BoolIfExists, not Bool

The key aws:MultiFactorAuthPresent has three states, not two:

true     signed in with MFA
false    signed in without MFA
MISSING  no label at all — this is what an access key looks like
Bool          deny if the label says false
              → a request with NO label is never matched → walks through
BoolIfExists  deny if it says false, OR if there is no label → closed

One word, and the policy looks identical in the console.

Plain Bool leaves access keys — the most common path into a compromised account — completely unaffected. It blocks the safe route and leaves the dangerous one open. That is the difference between enforcement and theatre.

A policy variable

"Resource": "arn:aws:iam::*:mfa/${aws:username}"

AWS substitutes whoever is calling. One policy, and everyone can manage only their own MFA. Without it, "let people manage MFA" would mean "let anyone remove anyone's MFA".

The test that failed first

A throwaway mfa-test user was given both AdministratorAccess and EnforceMFA, with no MFA device. On the first attempt it created an S3 bucket successfully.

create policy   a JSON document exists somewhere
attach policy   it begins affecting someone

A correct security policy sat in the account doing nothing.

That gap is where real breaches live — the policy is written, it appears in the list, the audit is ticked, and nothing is enforced. Testing found it in thirty seconds. Assuming would never have found it.

Once attached, the same user was refused: "You don't have permission to delete bucket." A full administrator, blocked. Deny beat Allow, in front of you.

Roles: a costume, not a person

user

permanent identity

  • Is a person
  • Has a password
  • May have access keys
  • You are it

role

worn temporarily

  • Is a set of permissions
  • Has no credentials at all
  • Assumed, then given back
  • You become it, for a while

A role has two policies — the second is unique to roles

trust policy        WHO may assume it      ← only roles have this
permissions policy  WHAT they can do then

Both must say yes. The trust policy introduces a part no identity policy needs — Principal — because an identity policy is already attached to an identity, while a role must name who may become it.

{
  "Effect": "Allow",
  "Principal": { "Service": "budgets.amazonaws.com" },
  "Action": "sts:AssumeRole"
}

The five trusted-entity choices in the console are just five shapes of Principal: an AWS service, another account, a web identity, a SAML directory, or hand-written JSON.

Why roles replaced access keys

the old way:  /home/app/.aws/credentials
              aws_access_key_id = AKIA...
✗Never expires — valid forever once stolen
✗Works from anywhere — a thief uses it from their own laptop
✗Rotating means touching every server, so nobody rotates
✗Copying it leaves no trace

With a role, the instance asks AWS, AWS checks the trust policy, and issues temporary credentials that rotate automatically. Nothing is stored on disk. A compromised instance leaks something that expires in hours and only does what the role allows.

Access keys are the old way. Roles are how AWS is actually built.

In a well-run account almost nothing has access keys — which is why root and yash-admin both have zero.

Assuming a role replaces your permissions

Observed directly, and it surprises almost everyone.

yash-admin                   can do everything
yash-admin wearing the role  can only read S3

An administrator assumed S3ReadOnlyRole and was then refused by EC2. You do not carry your own permissions into the role. While wearing it, you are only it.

User: arn:aws:sts::639679388494:assumed-role/S3ReadOnlyRole/yash-admin
      is not authorized to perform: ec2:DescribeInstances
      because no identity-based policy allows it
arn : aws : sts :: 639679388494 : assumed-role/S3ReadOnlyRole/yash-admin
             │                            │                  │
             │                            │                  └─ who is wearing it
             │                            └─ which costume
             └─ NOT iam. STS issues temporary credentials.

The ARN names both the role and the person, which is how CloudTrail can still attribute the action to you.

Two kinds of denial, needing opposite fixes

"no identity-based policy allows"  →  implicit deny. You are missing an Allow.
"explicit deny in a policy"        →  something is actively blocking you.

Adding permissions will never help against an explicit Deny. Reading that one line tells you which problem you have.

This is why mature AWS shops do not let anyone hold admin all day: a narrow role for routine work, a deliberate switch to a powerful one for the few minutes it is needed, then back. Smaller blast radius, and every assumption shows up in CloudTrail as a deliberate act.

The circuit breaker

A budget alert emails you. A budget action does something — with no human involved.

The design decision matters more than the wiring

The obvious policy is wrong:

{ "Effect": "Deny", "Action": "*", "Resource": "*" }   ← a trap

If that fires, you also cannot delete the expensive thing. The breaker locks you out of the cleanup while the bill keeps growing.

deny creation   stop the bleeding
allow deletion  keep the scalpel

Built here: a Deny on ec2:RunInstances, ec2:CreateNatGateway, rds:CreateDBInstance, elasticloadbalancing:CreateLoadBalancer and similar — with no Terminate, Delete or Describe anywhere in it.

A blunt guardrail must be manual, so it never fires. A precise one can be automatic, so it actually works.

A deny-everything breaker is too dangerous to auto-run, so it gets set to "require approval" — so it never fires at 3am, so it does not protect against the one scenario it exists for. Precision is not elegance here; it is what lets you turn the thing on.

AWS Budgets needed its own role to act on your behalf — trust policy principal budgets.amazonaws.com. The first place roles stopped being theory.

Words you now own

statement
One rule in a policy: Effect, Action, Resource, Condition.
implicit deny
The default. Nothing mentioned it, so it is denied.
explicit Deny
A policy actively said no. Beats every Allow.
NotAction
The inverse of Action — everything except these.
BoolIfExists
A condition that also matches when the key is absent.
${aws:username}
A policy variable. AWS substitutes the caller.
role
Permissions with no credentials, assumed temporarily.
trust policy
Who may assume a role. Only roles have one.
Principal
The "who" in a trust policy.
STS
The service that issues temporary credentials.
assumed-role ARN
Names both the role and the person wearing it.
budget action
A budget that does something, not just emails.
AWS managed policy
Written and updated by AWS. You cannot edit it.

Test yourself

Answer before looking anything up.

  1. You hold AdministratorAccess. One more policy denies s3:DeleteBucket. Can you delete a bucket? Can you still terminate EC2 instances? Why?
  2. Why can you not enforce a rule using only Allow?
  3. A policy grants s3:ListBucket on arn:aws:s3:::reports/*. What can the holder actually do, and why?
  4. Why might you deliberately grant GetObject without ListBucket?
  5. Explain the difference between Bool and BoolIfExists, and which real-world credential the difference protects against.
  6. Why does the MFA policy use NotAction rather than Action?
  7. What would go wrong if the MFA policy had no carve-out at all?
  8. Your first mfa-test run succeeded in creating a bucket. What was wrong, and what general lesson does that teach?
  9. Name the two policies a role has, and say which one a user never needs.
  10. You are an administrator. You assume a read-only role and EC2 refuses you. Why — and is that a bug?
  11. Read this and say what it tells you:
    arn:aws:sts::639679388494:assumed-role/S3ReadOnlyRole/yash-admin
  12. Two denial messages: "no identity-based policy allows" and "explicit deny in a policy". What is different, and why do they need opposite fixes?
  13. Why is a stolen role credential less dangerous than a stolen access key? Two reasons.
  14. Why does a budget breaker that denies everything end up protecting you less than one that denies only creation?
  15. Attaching a policy takes effect instantly, but MFA status does not change mid-session. Why are these different?
