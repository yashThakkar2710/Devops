Week 1 · Day 4 · 01-04

NAT, security groups and endpoints

A database in a private subnet needs security updates. The obvious fix — a route to the internet gateway — makes it public. Getting outbound without inbound is the whole day.

Why the obvious fix is wrong

private-1a  →  0.0.0.0/0 → my-igw

database  →  internet     allowed    what you wanted
internet  →  database     also allowed   what you just created

A route to an internet gateway works in both directions. There is no way to make it one-way. What you need is something else entirely.

You have already seen the answer working

Measured on this machine, in the networking work.

leaving the PC        FROM 192.168.31.9    private
leaving the router    FROM 152.59.39.80    rewritten to public

Your home router does this every day. Your laptop reaches the internet; the internet cannot reach your laptop. Nobody wrote a firewall rule for that.

the router keeps a note:
  "I sent a request to example.com on behalf of 192.168.31.9"

a reply to something I sent       a note exists  → forwarded
an unexpected inbound connection  no note        → dropped

One-way is a side effect of the rewriting, not a policy.

Outbound works because a note exists. Inbound fails because one does not. Nobody designed a rule for it — the asymmetry falls out of how translation works.

That rewriting is NAT. AWS sells it as a managed service, the NAT gateway. Same job as the box on your wall.

A public IP and a route are two different things

Would a NAT gateway work in a private subnet, if you gave it an Elastic IP? No — and the reason matters.

NAT asks:     where does 104.20.23.154 go?
route table:  10.0.0.0/16 local ... and nothing else
              → dropped

It has a perfectly good public address and no road.

A street address on a house with no road to it.

The postman knows where you live and still cannot get there — and you cannot leave either.

Both halves of the rule

route, no public IP   can go out via NAT, cannot be reached
public IP, no route   nothing works at all
both                  reachable both ways
neither               sealed

Every "is this reachable?" question in AWS is these two switches. The NAT lives in a public subnet precisely because that is where both are satisfied.

The single-AZ failure, and why AWS added a fix

The console now offers Regional and Zonal modes. Zonal was chosen deliberately.

my-nat lives in public-1a (building A)
private-1b routes 0.0.0.0/0 → my-nat

building A fails
  → the NAT is gone
  → private-1b has a route pointing at nothing
  → building B is healthy and its servers are cut off anyway

The classic fix, and the exam answer

public-1a  →  nat-1a       private-rt-a  →  0.0.0.0/0 → nat-1a
public-1b  →  nat-1b       private-rt-b  →  0.0.0.0/0 → nat-1b

One NAT per AZ, one private route table per AZ. Cost: two NAT gateways, roughly $64/month — which is why many small setups knowingly accept the risk and run one. A real trade-off, not an obvious win.

Regional mode is AWS solving this inside the product. Worth knowing it exists; not worth learning instead of the zonal model, which is what the exam was written around.

Two guards, and only one takes notes

Every conversation has two directions. The question is whether you need a rule for each. Switch between them.

Why it is called stateful

a guard who takes notes
  visitor arrives   → on the list → let in, and write it down
  visitor leaves    → check the notebook → let out

a guard with no notes
  visitor arrives   → on the IN list → let in
  visitor leaves    → no memory → check a separate OUT list → blocked

Forgetting the second NACL rule is one of the most common AWS mistakes.

The request arrives, the reply is silently dropped, the page never loads — and the inbound rule sits there looking completely correct. With a security group that cannot happen.

The other three differences

security group

attached to a resource

  • Stateful — replies are automatic
  • Guards one server's door
  • Allow only — cannot deny
  • No order; any allow is enough
  • Default: deny in, allow out

NACL

attached to a subnet

  • Stateless — both directions needed
  • Guards the whole street entrance
  • Allow and deny
  • Numbered; first match wins
  • Default: allow everything, both ways

Two servers in one subnet can have completely different rules, because each has its own guard at its own door. The subnet does not decide.

Order matters enormously on a NACL

rule 100   DENY   203.0.113.50     matched first → stop
rule 200   ALLOW  0.0.0.0/0        never read for that address

rule 100   ALLOW  0.0.0.0/0        matches everyone, including the bad one
rule 200   DENY   203.0.113.50     never reached. the block does nothing.

Security groups have no order — all rules are evaluated and any allow is sufficient. That is what makes several of them safe to attach at once.

A security group cannot say "block this one address".

Same shape as IAM: Allow grants, Deny blocks, and you need Deny to build a guardrail. NACLs exist for exactly what security groups structurally cannot do.

The layers, outside in

internet
   ▼
route table      does a path exist?
   ▼
NACL             subnet border    stateless, ordered, can deny
   ▼
security group   the door         stateful, unordered, allow-only
   ▼
the server

Any one says no and it is blocked. Checking them outside-in is the professional diagnostic order.

Which to actually use

security groups   for essentially everything
NACLs             leave at the default unless you need a blanket DENY

The default NACL allows everything both ways, deliberately, so it stays out of the way. Most companies never touch it.

The endpoint that removes the NAT entirely

without:  private subnet → NAT → IGW → the public internet → S3
with:     private subnet → endpoint → S3   never leaves AWS

S3 is an AWS service in the same region. Without an endpoint the traffic leaves AWS and comes straight back — paying NAT data charges and crossing the public internet to reach a service next door.

Two kinds, and the difference is exam-critical

Gateway     S3 and DynamoDB only.      a route table entry.   free
Interface   almost everything else.   a network card with a
                                      private IP in your subnet.  paid

Exam trap: both types now exist for S3.

A question that mentions cost wants the gateway endpoint. Identical service name, very different bill.

It wrote its own route

pl-78a54011 (…ap-south-1.s3)   →  vpce-02056949513302f39   Active
0.0.0.0/0                      →  nat-...                  Active
10.0.0.0/16                    →  local                    Active

That first line appeared on its own. pl- is a prefix list — AWS's managed list of every IP range S3 uses in this region, kept updated by AWS. You reference the list, never the addresses.

Most specific wins, so S3 traffic silently takes the free private path and everything else still goes via NAT. The same rule from day 3, now doing real work.

Teardown, and two things it teaches

Blackhole

0.0.0.0/0    nat-0a27882dca7762a5f    ⚠️ Blackhole

A route pointing at something that no longer exists. Traffic matches the rule and then evaporates, with no error anywhere.

In a real job, "blackhole" in a route table is frequently the answer to "it worked yesterday".

Elastic IPs charge when idle

attached to something running   free
sitting unattached              ~$3.60/month

Deleting the NAT leaves its address allocated and billing. This is the one people forget. AWS charges for held-but-unused public addresses deliberately — IPv4 addresses are scarce, and hoarding should cost something.

End state

✓my-vpc, subnets, route tables, my-igw — free
✓s3-endpoint (Gateway) — free
✗my-nat — deleted
✗blackhole route — removed
✗Elastic IP — released

The private subnets now reach S3 and nothing else. No internet, no NAT, no cost — and a lot of real architectures look exactly like this.

Words you now own

NAT
Rewriting the sender address at a boundary. Outbound-only falls out of it.
NAT gateway
AWS's managed NAT. Lives in a public subnet, needs an Elastic IP.
Elastic IP
A public address you own. Free while attached, charged while idle.
security group
Firewall on a resource. Stateful, allow-only, unordered.
stateful
Replies are allowed automatically because the request was.
NACL
Firewall on a subnet. Stateless, allow and deny, numbered.
stateless
No memory. Each direction needs its own rule.
VPC endpoint
A private door from your VPC to an AWS service.
gateway endpoint
S3 and DynamoDB only. A route table entry. Free.
interface endpoint
Most other services. A network card in your subnet. Paid.
prefix list
An AWS-maintained list of IP ranges you reference by name.
blackhole
A route whose target no longer exists. Traffic vanishes silently.
