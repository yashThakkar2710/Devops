Journey of a request

Everything on this page comes from the capture you recorded in lab 00-01: 33 packets, 299 milliseconds, one visit to example.com. Nothing here is an example — it is your machine.

What is a network?

Start here. Nothing below assumes you know anything.

A network is two or more computers that can send each other messages. That is the whole definition. Everything else in this curriculum is detail about how that happens reliably, quickly and securely.

You need one because the thing you want — a web page, a file, a message — is sitting on a different computer than the one in front of you.

They are not plugged into each other

Your laptop is not wired to a server in another country. The message travels in short jumps, machine to machine:

your laptop172.26.1.224
→
home routerthe box on your wall
→
your ISPAirtel, Jio, …
→
≈ 10 moreundersea cables, other countries
→
the server104.20.23.154

No machine in that chain knows the whole route. Each one knows only where to pass the message next — like asking for directions at every corner instead of memorising the map. That single idea is what allows the internet to be enormous and to keep working when parts of it break.

What physically travels

Electricity down copper wire. Light down glass fibre. Radio through the air. They look completely different, but all three carry the same thing: ones and zeros. On or off, over and over, very fast.

Everything above that — every address, every page, every video call — is agreements about what particular patterns of ones and zeros mean.

Why it is cut into pieces

A message is not sent in one go. It is cut into small chunks, and each chunk is called a packet. Three reasons:

The line is shared

Everyone on the internet uses the same cables. If one person sent a 2 GB file as a single unbroken stream, everyone else would wait for it to finish.

Losing a little beats losing a lot

Something in the middle will occasionally drop a packet. Resending one small chunk is cheap. Resending a whole film is not.

Pieces can take different routes

If one path gets congested or breaks, later packets simply go another way. Nothing has to be restarted.

It is moving house. You cannot post a sofa, so you send many labelled boxes, and the person at the other end puts everything back together.

So what is "the internet"?

Many separate networks — your home, your office, a university, a hosting company — that have agreed to pass each other's packets along. There is no central computer running it. It is an agreement, kept by millions of machines independently.

The rest of this page is one real message making that journey, and coming back.

Port 53 means name lookups everywhere in the world. Port 443 means encrypted web, everywhere. These are fixed agreements, not settings on your machine — which is the only reason a computer you have never met knows what you are asking for.

Your own port, 59573, was picked at random a moment before you sent the question. It exists so that when an answer arrives, your computer knows which of its running programs was waiting for it.

Your machine has two doors

A network interface is a way out of your computer. Run ip -br addr show to see yours.

eth0

the real door

┌──────────┐
│ your     │ eth0
│ computer │ ════► router ► internet
└──────────┘

eth is short for Ethernet, 0 means the first one. Its address is 172.26.1.224. Packets through this door leave the machine.

lo

the door back into the same room

┌──────────┐
│ your  ┌──┴──┐
│ comp. │ lo  │ out… and straight back
│       └──┬──┘
└──────────┘

lo is short for loopback. Its address is 127.0.0.1. Packets through this door never leave. This is what localhost:3000 has always been.

Why have a fake door at all? Programs on one machine need to talk to each other. Rather than invent a second system for that, they reuse the network — through a door that leads back inside. Same addresses, same ports, same rules, no cable.

Two ways to spot loopback in a capture

12:44:53.223421 eth0 Out IP 172.26.1.224 > 1.1.1.1.53
12:44:53.333082 lo   In  IP 10.255.255.254 > 10.255.255.254.53

The interface name is the second item on every line. And on a loopback line the two addresses are identical — the machine is both sender and receiver.

So what is "my IP address"?

A machine does not have one address. It has one per door, and a few extra. All of them are correct at the same time.

addresslives onwho can see it
127.0.0.1loonly programs on this machine
10.255.255.254loonly WSL's own DNS helper
172.26.1.224eth0your Windows machine and its network
172.26.0.1the routerthe way out of your neighbourhood
(your public one)your ISPthe entire internet

Find the last one with curl -s ifconfig.me. It is not the same as any address on your machine — your router owns it, and everything in your house shares it. Why that works is Phase 2, under the name NAT.

The slash number

An address is written 172.26.1.224/20. The number after the slash says how big your neighbourhood is.

writtenaddresses in the neighbourhood
/321 — just this address, alone
/24256
/204,096
/816,777,216

A bigger number means a smaller neighbourhood. That feels backwards and it is explained properly in Phase 2. For now: 10.255.255.254/32 is a neighbourhood of exactly one — that DNS helper stands alone. 172.26.1.224/20 puts you among 4,096 addresses, and your Windows machine is one of your neighbours.

Direct, or via the router?

Before sending anything, your machine asks one question: is this address in my neighbourhood? You can watch it decide, without sending a single packet.

ip route get 172.26.1.99a neighbour
172.26.1.99 dev eth0 src 172.26.1.224

No via. Straight there.

ip route get 8.8.8.8a stranger
8.8.8.8 via 172.26.0.1 dev eth0 src 172.26.1.224

There is a via. Hand it to the router and let them deal with it.

ip route get 127.0.0.1myself
local 127.0.0.1 dev lo src 127.0.0.1

Never leaves the machine.

The entire rulebook is two lines

ip route showevery rule your machine has
default       via 172.26.0.1 dev eth0
172.26.0.0/20               dev eth0

Read it as a single question:

Is the address inside 172.26.0.0/20?
   yes → send it straight out eth0
   no  → "default" → give it to 172.26.0.1

default means anything I do not recognise. Every address on the internet that is not your neighbour — billions of them — falls into that one line.

This is the idea from the top of the page, now in front of you. Your machine has no idea where 8.8.8.8 is. It only knows: not mine, give it to the router. The router then asks itself the same question, and so does the next one, all the way there.

The name lookup, both halves

Two packets. A question and its answer. Notice what swaps between them.

0 ms
Out172.26.1.224.59573 > 1.1.1.1.53  A? example.com.

Where does example.com live?

83 ms
In1.1.1.1.53 > 172.26.1.224.59573  A 104.20.23.154

At 104.20.23.154.

The addresses and ports are identical in both lines, just reversed. That reversal is the whole mechanism: it is how your computer matches an answer to the question it asked, with no memory of the conversation required anywhere in between.

Your capture shows this happening twice. Lines 1–2 are dig, a tool whose only job is asking name questions — the lab runs it so a lookup is guaranteed to appear. Lines 3–6 are curl doing its own. Neither program knew the other had asked. Programs do not share name answers with each other.

Lines 3–6: two questions, and why they need numbers

The second lookup is the most interesting thing in your capture. Four packets, on loopback, and the answers come back in the wrong order.

3  .333082  lo  10.255.255.254.42162 > …53   47200+  A?    example.com.
4  .333109  lo  10.255.255.254.42162 > …53   38510+  AAAA? example.com.
5  .366140  lo  …53 > 10.255.255.254.42162   38510   AAAA  2606:4700:9a65:…
6  .370801  lo  …53 > 10.255.255.254.42162   47200   A     104.20.23.154, 172.66.147.243

Two kinds of address exist

questionasking forlooks like
A?an IPv4 address104.20.23.154
AAAA?an IPv6 address2606:4700:9a65:72db:…

IPv4 uses four numbers, which allows about 4.3 billion addresses. In the 1980s that was unimaginably many. It ran out. IPv6 is the replacement, long enough to have no practical limit. The world has been moving across for twenty-five years and is not finished, so programs ask for both and use whichever works.

Note the timestamps: .333082 and .333109. Twenty-seven microseconds apart. curl did not ask, wait, then ask again — waiting would have doubled the delay.

The answers arrive in the wrong order

asked

47200A?
38510AAAA?

answered

38510AAAA, first back
47200A, second back

The first question was answered second. Now look at why that is a problem — the two questions were sent from the same port:

line 3:  10.255.255.254.42162 > 10.255.255.254.53
line 4:  10.255.255.254.42162 > 10.255.255.254.53
                        ↑ identical ↑

Same sender, same port, same destination, same port. Two replies land in the same place and look the same from the outside. The only thing telling them apart is the number stamped on each one: 47200 and 38510. It is copied from the question onto its answer, and it is called the transaction ID.

You watched the exact problem that ID exists to solve.

Most people learn "a name lookup has a transaction ID" as a fact to memorise. You saw the out-of-order delivery that makes it necessary. There is a second, security-related reason for that number being random rather than sequential — Phase 4.

One name, two addresses

6   47200  2/0/0  A 104.20.23.154, A 172.66.147.243

Two answers. example.com has two addresses, and either works — if one server dies the other still answers. Your machine used the first, which is why packet 7 goes to 104.20.23.154.

It got an IPv6 address and ignored it

Line 5 handed over a perfectly good IPv6 address. Packet 7 used IPv4 anyway. The reason is on your own machine:

$ ip -6 route show default
(nothing)

$ curl -6 https://example.com   → failed
$ curl -4 https://example.com   → 200 OK

There is no IPv6 route out of WSL. The fe80:: address on eth0 is local-only and cannot leave the machine. So the IPv6 answer was unusable, and IPv4 was used instead.

That quiet fallback has a name — Happy Eyeballs — and it is why twenty-five years of IPv6 rollout has not broken the web. Things try both and use what works, without telling you.

Where the 299 milliseconds went

All 33 packets, drawn to scale. Each block is real elapsed time from your capture.

259 ms of getting ready. 11 ms of actually talking.

Finding the address, agreeing to connect, and proving identity took 87% of the time. The page itself — the thing you wanted — arrived in the last few percent. Most of what makes the modern web fast is the long fight to shrink those first three blocks.

Words you now own

packet
One small chunk of a message. Big things are cut into many.
IP address
Which machine. 172.26.1.224 is yours; 104.20.23.154 is the server you reached.
port
Which program inside that machine. 53 is name lookups, 443 is encrypted web.
DNS
The system that turns a name into an address.
capture
A saved recording of packets. Yours is out/capture.pcap.
tcpdump
The tool that records packets and prints them as text.
interface
A door out of your machine. eth0 goes outside; lo loops back to itself.
loopback
The interface that never leaves the machine. 127.0.0.1, also known as localhost.
curl
A program that fetches things from the internet and prints them. A browser with no window.
dig
A program whose only job is asking name questions.
A record
An IPv4 address for a name.
AAAA record
An IPv6 address for a name.
transaction ID
A number stamped on a name question and copied onto its answer, so replies can be matched to questions.
router
The machine you hand a packet to when the destination is not your neighbour. Yours is 172.26.0.1.
default route
The rule that catches every address you do not recognise.
/20, /32
How big your neighbourhood is. Bigger number, smaller neighbourhood.

What the flags mean

-r
read from a saved file instead of the live network
-nn
show raw numbers — do not turn addresses into names or ports into service names. Without this, tcpdump makes extra lookups that pollute what you are trying to watch.
-i any
record from every interface at once (used by capture.sh)
-w file
write packets to a file instead of the screen
-s
curl: stay silent, no progress bar
-o /dev/null
curl: throw the page away. The lab uses this because it wants the packets, not the page — which is why curl appeared to do nothing.
-4 / -6
curl: force IPv4 or IPv6 only, instead of choosing
-br
ip: brief output, one line per interface
